ARCHITECTURE 05

Eventarc と Pub/Sub：配送の失敗を誰が引き受けるか

GCS へのアップロードを 2 段の Cloud Functions Gen2 に流す。前段は Eventarc トリガー、後段はあえて Pub/Sub の Push サブスクリプションを自分で書いてある。同じ「イベントで関数を起動する」でも、失敗したメッセージの行き先が違うことを実測で確かめるテーマ。

Cloud Functions Gen2 (nodejs22) Eventarc Pub/Sub + DLQ asia-northeast1 min_instance = 0 なので待機課金は無い。ただし GCS 3 バケット・関数イメージ・DLQ 滞留メッセージは残る

このテーマで学ぶこと

各項目には、それを自分の目で確かめる手順が紐づいている。

1

Eventarc トリガーと自作 Push サブスクリプションでは、握れる「失敗時の挙動」が違う

GCS → processor は google_eventarc_trigger、processor → subscriber は google_pubsub_subscription の push_config で繋いである。後者を手で書いたからこそ dead_letter_policy と retry_policy（10s〜600s のバックオフ）が指定できる。Eventarc トリガー側は retry_policy.max_attempts しか持たず、しかもこのコードでは 1 にしてある。

→ 確認 1：2 つの配送経路の設定を並べて見る
2

DLQ は「5 回失敗したあと」に初めて動く。保持設計もそこだけ別扱いにする

max_delivery_attempts = 5 なので、1 回落ちただけでは DLQ に行かない。通常トピックの保持が 1 日（86600s）なのに対し DLQ は 7 日（604800s）、監視用の test-dlq-monitor は retain_acked_messages = true かつ expiration_policy.ttl = ""（無期限）。失敗を「その場で捌く」のではなく「後から解析する」ための持ち方になっている。

→ 確認 2：わざと失敗させて DLQ に落とす
3

自分で作った SA に権限を付けるだけでは動かない — Google 管理のサービスエージェントに渡す権限がある

modules/service_account が作る SA は 3 つだが、modules/iam はそれ以外に GCS サービスエージェントへ pubsub.publisher（Eventarc の GCS イベントは裏で Pub/Sub を通るため）、Pub/Sub サービスエージェントへ DLQ トピックの publisher と eventarc_invoker_sa への iam.serviceAccountTokenCreator（Push の OIDC トークンを発行するためのなりすまし）を与えている。「動かないときはまずサービスエージェントを疑う」という嗅覚がここで身につく。

→ 確認 3：サービスエージェントに付いた権限を目視する
4

ingress（ネットワーク到達性）と run.invoker（認証）は別レイヤ

両関数とも ingress_settings = "ALLOW_INTERNAL_ONLY" で、外から URI を直接叩いても届かない。それでも Eventarc と Pub/Sub Push は、同一プロジェクトかつ run.app URL 宛であれば内部トラフィックとして扱われるので処理は流れる。外部に一切公開せずイベント駆動を組めるのはこの性質による。

→ 確認 4：直叩きは弾かれるのに GCS 経由では動く

何を作ったか

input バケットへのアップロードを起点に、processor がメタデータを Pub/Sub へ publish し、subscriber が output バケットへ JSON を書く 2 段パイプライン。

architecture.svg（クリックで拡大）
モジュール役割効いている設定
modules/apis 必要な API を有効化 disable_on_destroy = false / 7 API
modules/service_account 処理用 2 つ + 呼び出し用 1 つの SA test-gcf-processor-sa / -subscriber-sa / -eventarc-invoker-sa
modules/storage input / output / 関数ソース用の 3 バケット test-{input,output,functions-source}-<プロジェクト番号>、全て force_destroy = true
modules/topics 出力トピック・DLQ トピック・DLQ 監視用 Pull サブスク 保持 86600s / DLQ 604800s、retain_acked_messages = true
modules/functions processor / subscriber の Gen2 関数と ZIP 配置 256M / timeout 60s / max 3 / min 0 / ALLOW_INTERNAL_ONLY
modules/triggers GCS→processor の Eventarc、Pub/Sub→subscriber の Push サブスク Eventarc max_attempts = 1 ⇔ Push max_delivery_attempts = 5 + backoff 10s〜600s
modules/iam 自作 SA + Google 管理サービスエージェントへの権限付与 gs-project-accounts → pubsub.publisher、gcp-sa-pubsub → serviceAccountTokenCreator

設計の要点

「そう書いてある」ではなく「そう書いた理由」。裏取りできていないものは仮説と明記する。

後段だけ Eventarc を使わず Push サブスクリプションを手書きしている

google_eventarc_trigger は retry_policy.max_attempts しか持たず、DLQ の受け皿を指定できない。DLQ とバックオフを効かせたい区間だけサブスクリプションを自分で定義する、という切り分けになっている。前段を max_attempts = 1 にしてあるのは、その対比を出すための意図的な設定と読める（仮説）。

ソース ZIP のオブジェクト名に output_md5 を埋め込む

processor-${data.archive_file.processor.output_md5}.zip のように名前へハッシュを入れてある。名前が固定だと index.js を書き換えても google_storage_bucket_object の属性しか変わらず、関数の再デプロイが走らない。Terraform で Functions を扱うときの定番の回避策。

学習用の割り切り

3 バケットとも force_destroy = true、project_id は "your-project-id" のままのプレースホルダ、main/ に outputs.tf が無い（apply 後の値は gcloud で引く）。本番運用ではいずれもそのままにしない。

どう確認するか

main/ に outputs.tf が無いので、バケット名はプロジェクト番号から組み立てる。

共通の準備

PROJECT_ID=$(gcloud config get-value project)
PROJECT_NUMBER=$(gcloud projects describe "$PROJECT_ID" --format='value(projectNumber)')
REGION=asia-northeast1
INPUT_BUCKET="test-input-$PROJECT_NUMBER"; OUTPUT_BUCKET="test-output-$PROJECT_NUMBER"
echo '{"hello":"05"}' > /tmp/t.json
確認 1

2 つの配送経路の設定を並べて見る

同じ「イベントで関数を起動する」経路が、失敗時にどこまで面倒を見るかを設定の差として確かめる。 ↑ 学び 1

手順
gcloud eventarc triggers describe test-gcs-to-processor --location="$REGION" \
  --format='yaml(eventFilters, destination.cloudRun.service, retryPolicy)'

gcloud pubsub subscriptions describe test-subscriber \
  --format='yaml(pushConfig.pushEndpoint, deadLetterPolicy, retryPolicy)'
期待される結果
  • Eventarc 側：retryPolicy.maxAttempts: 1 のみ。deadLetterPolicy というフィールドはそもそも出力に存在しない
  • Pub/Sub 側：deadLetterPolicy.maxDeliveryAttempts: 5 と deadLetterTopic に test-dlq が入っている
  • Pub/Sub 側：retryPolicy.minimumBackoff: 10s / maximumBackoff: 600s
これでわかること
失敗の受け皿を持てるのは、自分で書いたサブスクリプションの側だけ。GCS → processor の失敗は 1 回試して捨てられ、どこにも記録が残らない。DLQ が要る区間はマネージドなトリガーに任せきらない、という判断がここに現れている。
確認 2

わざと失敗させて DLQ に落とす

subscriber の書き込み権限を剥がし、5 回のリトライを経てメッセージが DLQ に現れることを見る。 ↑ 学び 2

手順
gcloud storage buckets remove-iam-policy-binding "gs://$OUTPUT_BUCKET" \
  --member="serviceAccount:test-gcf-subscriber-sa@$PROJECT_ID.iam.gserviceaccount.com" \
  --role=roles/storage.objectCreator
gcloud storage cp /tmp/t.json "gs://$INPUT_BUCKET/fail.json"   # 5〜10 分待つ
gcloud pubsub subscriptions pull test-dlq-monitor --limit=5 --format='value(message.data)'
期待される結果
  • test-dlq-monitor から fail.json を含む JSON が引ける（--auto-ack を付けなければ残る）
  • 1 回目の失敗直後には出てこない。maxDeliveryAttempts: 5 とバックオフ 10s→600s の分だけ遅れる
  • いつまで待っても出てこない場合は IAM 不足を疑う（→ つまずき 2）
これでわかること
DLQ は「失敗したら即座に隔離する仕組み」ではなく「規定回数を使い切った先の終点」。max_delivery_attempts とバックオフの組み合わせが、障害検知までの遅れをそのまま決める。終わったら剥がした roles/storage.objectCreator を add-iam-policy-binding で戻すこと（戻さないと以降の確認が全部失敗する）。
確認 3

サービスエージェントに付いた権限を目視する

自分が google_service_account で作っていない SA に、どんな権限が渡っているかを確かめる。 ↑ 学び 3

手順
gcloud projects get-iam-policy "$PROJECT_ID" --flatten='bindings[].members' \
  --filter='bindings.members~(gcp-sa-pubsub|gs-project-accounts|gcf-admin-robot)' \
  --format='table(bindings.role, bindings.members)'

gcloud iam service-accounts get-iam-policy \
  "test-eventarc-invoker-sa@$PROJECT_ID.iam.gserviceaccount.com" --format='yaml(bindings)'
期待される結果
  • service-$PROJECT_NUMBER@gs-project-accounts.iam.gserviceaccount.com に roles/pubsub.publisher
  • SA ポリシー側に roles/iam.serviceAccountTokenCreator が service-$PROJECT_NUMBER@gcp-sa-pubsub... 宛で付いている
  • これらは gcloud iam service-accounts list には出てこない（プロジェクト内の SA ではない）
これでわかること
GCS イベントの配送も、Push サブスクリプションの OIDC トークン発行も、Google 側のエージェントが自分の代わりに実行している。だから「自作 SA には全部権限を付けたのに動かない」が起きる。権限エラーのメールアドレスに gcp-sa- や gs-project-accounts が見えたらこの類。
確認 4

直叩きは弾かれるのに GCS 経由では動く

外部からの HTTP は届かないのに、Eventarc 経由の同じエンドポイントは動くことを対比する。 ↑ 学び 4

手順
gcloud functions describe test-processor --region="$REGION" --v2 \
  --format='value(serviceConfig.ingressSettings, serviceConfig.uri)'
URI=$(gcloud functions describe test-processor --region="$REGION" --v2 --format='value(serviceConfig.uri)')
curl -s -o /dev/null -w '%{http_code}\n' "$URI"
gcloud storage cp /tmp/t.json "gs://$INPUT_BUCKET/ok.json" && sleep 30
gcloud storage ls "gs://$OUTPUT_BUCKET/processed/"
期待される結果
  • ingressSettings は ALLOW_INTERNAL_ONLY
  • curl の HTTP ステータスは 200 にならない（ingress で落とされるため 404、認証で落ちる場合は 403）
  • それでも gs://$OUTPUT_BUCKET/processed/ok.json.json が生成されている
これでわかること
ingress は「どこから来た通信か」、roles/run.invoker は「誰として来たか」で、別々に効く。Eventarc / Pub/Sub Push は同一プロジェクト + run.app URL であれば内部扱いになるので、公開エンドポイントを一切持たないままイベント駆動を成立させられる。

後始末とつまずき

後始末：課金を止める

min_instance_count = 0 なので待機インスタンスの課金は無い。残るのは GCS 3 バケット、Gen2 関数のビルド成果物（Artifact Registry のイメージ）、そして retain_acked_messages = true と無期限 TTL のせいで自然消滅しない DLQ 監視サブスクリプション。

terraform -chdir=architectures/05/main destroy
gcloud functions list --regions=asia-northeast1
gcloud pubsub topics list --format='value(name)'
gcloud artifacts repositories list --location=asia-northeast1

つまずき 1：project_id がプレースホルダのまま（2 箇所）

main/local.tf:5 の project_id = "your-project-id" と main/provider.tf:16 の project は別々に書かれていて、両方を直さないと apply が通らない。outputs.tf も無いので、apply 後の値は上の「共通の準備」のように gcloud から引くことになる。

つまずき 2：DLQ の IAM が 1 つ足りない可能性

公式ドキュメントによると DLQ 転送には DLQ トピックへの publisher と 元サブスクリプションへの subscriber の両方が Pub/Sub サービスエージェントに要る。modules/iam/main.tf にあるのは前者だけで、後者が無いと転送後にサブスクリプションからメッセージを削除できず、確認 2 で DLQ にいつまでも現れないことがある。未検証なので、実際に踏んだら次で補う。

gcloud pubsub subscriptions add-iam-policy-binding test-subscriber \
  --member="serviceAccount:service-$PROJECT_NUMBER@gcp-sa-pubsub.iam.gserviceaccount.com" \
  --role=roles/pubsub.subscriber

つまずき 3：コード中の説明文と実際の配線が食い違っている

modules/functions/main.tf の subscriber の description と source/subscriber/index.js のコメントは「Eventarc (Pub/Sub topic.messagePublished) で起動」と書いてあるが、実際には Eventarc トリガーは作っておらず Push サブスクリプション経由。gcloud eventarc triggers list にトリガーが 1 つしか出ないのは正常で、探し回る前にこの食い違いを思い出すこと。

理解度チェック

設定を思い出せるかではなく、理由を自分の言葉で説明できるかを問う。チェック状態はこのブラウザに保存される。

  • 後段だけ Eventarc トリガーを使わなかった理由を、Eventarc 側で書けない設定を挙げて説明できる
  • あるメッセージが DLQ に到達するまでに何回・どれくらいの時間がかかるかを、コード中の値から見積もれる
  • 自作 SA ではないどの SA にどんな権限が必要で、それぞれ何のために使われるかを 3 つ挙げられる
  • ALLOW_INTERNAL_ONLY なのに Eventarc からは呼べる理由を、ingress と IAM を区別して説明できる
