ARCHITECTURE 01

Cloud Run を LB 経由で公開し、入口を一つに絞る

独自ドメイン、HTTPS、Cloud Armor を External Application Load Balancer に集め、Cloud Run の既定 URL を迂回できないことを確認する。

このテーマで学ぶこと

各項目には、それを自分の目で確かめる手順が紐づいている。

1

独自ドメインの HTTPS は、Cloud Run ではなくロードバランサーで受ける

グローバル IP、DNS の A レコード、Certificate Manager の DNS 認証、証明書マップを組み合わせると、ブラウザの入口を一つにできる。Serverless NEG は、その入口から Cloud Run をバックエンドとして扱うための接続点になる。

→ 確認 1：証明書・HTTPS・リダイレクトを確認する
2

Cloud Run の IAM と Ingress は、公開可否と到達経路を別々に決める

ブラウザからアクセスさせるため、この構成では allUsers に Invoker を付与する。それでも INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER を指定すれば、インターネットから run.app の既定 URL を直接通る経路は使えない。

→ 確認 2：LB 経由と既定 URL を比較する
3

Cloud Armor の国コード条件は、Cloud Run の前で通過を分ける

優先度 100 の origin.region_code == 'JP' を通し、それ以外を既定の 403 で拒否する。これはアクセス元を絞る入口制御であって、利用者本人を識別する認証ではない。

→ 確認 3：国内外で応答を比べる

何を作ったか

Cloud DNS → External Application Load Balancer → Cloud Armor → Serverless NEG → Cloud Run の公開経路。

architecture.svg（クリックで拡大）
モジュール役割効いている設定
cloud_run ブラウザ向けアプリケーションのバックエンド INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER、0〜3 インスタンス
load_balancer 独自ドメインの HTTP(S) 公開入口 EXTERNAL_MANAGED、Serverless NEG、TLS 1.2 以上
cloud_armor LB のバックエンドへ入る前のアクセス制御 origin.region_code == 'JP' を許可、既定は deny(403)
cloud_dns 独自ドメインと証明書 DNS 認証のレコード管理 A レコードと CNAME レコード、TTL は 300

設計の要点

今回のテーマ内で、選択した理由だけを残す。

Ingress は INTERNAL_ONLY ではなく INTERNAL_LOAD_BALANCER

External Application Load Balancer を Cloud Run の入口にするため、LB 経由を許可する Ingress 値を選ぶ。INTERNAL_ONLY のままでは、この LB から Cloud Run へ届かない。

ブラウザ公開と直アクセス防止を、同じ設定に混ぜない

Invoker の allUsers はブラウザからの呼び出しを成立させる設定であり、Ingress はどのネットワーク経路で届くかを制限する設定である。二つを合わせて、サービスアカウントをブラウザへ配らずに LB を唯一の入口にする。

作成・確認・削除までを一回の学習にする

Cloud Run の最小インスタンスを 0 にしても、LB と Cloud Armor には時間課金がある。常設の運用を扱うテーマではないため、約 3 時間の確認を終えたら削除する。

どう確認するか

先に main/local.tf のプロジェクト ID とドメインを自分の値へ置き換え、レジストラから Cloud DNS のネームサーバーへ委任してから apply する。

共通の準備

PROJECT_ID=your-gcp-project-id
DOMAIN=dev.your-domain.example
LB_IP=$(gcloud compute addresses describe test-lb-ip --global --project="$PROJECT_ID" --format='value(address)')
確認 1

証明書・HTTPS・リダイレクトを確認する

DNS 認証済みの証明書が有効になり、HTTP が HTTPS へ集約されていることを確かめる。 ↑ 学び 1

手順
gcloud certificate-manager certificates describe test-lb-cert --location=global --project="$PROJECT_ID" --format='value(managed.state)'
curl -sI --resolve "$DOMAIN:80:$LB_IP" "http://$DOMAIN/"
curl -sI --resolve "$DOMAIN:443:$LB_IP" "https://$DOMAIN/"
期待される結果
  • 証明書の状態が ACTIVE になる。
  • HTTP の応答は 301、Location は HTTPS の URL になる。
  • 日本国内の IP から HTTPS へアクセスすると 200 になる。
これでわかること
証明書と HTTP→HTTPS の処理は Cloud Run コンテナではなく、ロードバランサーの入口で完結している。
確認 2

LB 経由と既定 URL を比較する

Invoker が公開でも、インターネットからの直アクセスを Ingress で止められていることを確かめる。 ↑ 学び 2

手順
SERVICE_URL=$(gcloud run services describe test-cloud-run-service --region=asia-northeast1 --project="$PROJECT_ID" --format='value(status.url)')
curl -s -o /dev/null -w 'run.app: %{http_code}\n' "$SERVICE_URL"
curl -s -o /dev/null -w 'LB: %{http_code}\n' --resolve "$DOMAIN:443:$LB_IP" "https://$DOMAIN/"
期待される結果
  • run.app の既定 URL は 2xx にならない。
  • 日本国内の IP からの LB 経由は 200 になる。
  • 2 つの違いは IAM ではなく、Ingress が許可する経路で生じる。
これでわかること
認証を要求しない Cloud Run でも、LB を経由する公開経路だけを残せる。ブラウザにサービスアカウントを持たせる必要はない。
確認 3

国内外で応答を比べる

Cloud Armor の国別条件が、Cloud Run に届く前に結果を分けることを確かめる。 ↑ 学び 3

手順
gcloud compute security-policies describe test-cloud-armor-security-policy --global --project="$PROJECT_ID" --format='yaml(rules)'
curl -s -o /dev/null -w '%{http_code}\n' --resolve "$DOMAIN:443:$LB_IP" "https://$DOMAIN/"

上の curl を日本国内の回線と日本国外の回線で一度ずつ実行する。

期待される結果
  • ポリシーには優先度 100 の JP 許可ルールと既定の deny(403) が表示される。
  • 日本国内の回線は 200、日本国外の回線は 403 になる。
これでわかること
Cloud Armor はバックエンドサービスに関連付けることで、Cloud Run に到達する前に通過可否を決める。国コードは本人確認ではない。

後始末とつまずき

後始末：課金を止める

Cloud Run の最小インスタンスを 0 にしても、External Application Load Balancer、Cloud Armor、Cloud DNS ゾーンは残している間に費用が発生する。

terraform -chdir=architectures/01/main destroy
gcloud compute forwarding-rules describe fwdrule-test-https --global --project="$PROJECT_ID"
gcloud dns managed-zones describe example-zone --project="$PROJECT_ID"

destroy 後、後ろの二つは NOT_FOUND になればよい。ドメイン登録事業者で設定したネームサーバーは Terraform 管理外なので、戻すかどうかを別途判断する。

Cloud DNS ゾーンを作っただけでは証明書を発行できない

Terraform はゾーン内の A/CNAME レコードを作るが、登録済みドメインをそのゾーンへ委任する操作は含まれない。証明書が ACTIVE にならないときは、DNS 委任と認証用 CNAME を先に確認する。

理解度チェック

設定値を覚えたかではなく、理由を自分の言葉で説明できるかを問う。チェック状態はこのブラウザに保存される。

  • 独自ドメインの HTTPS を LB で受け、Serverless NEG で Cloud Run へつなぐ理由を説明できる。
  • allUsers の Invoker と INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER が、別の役割を持つことを説明できる。
  • Cloud Armor の国コード条件で分かることと、分からないことを説明できる。
  • 最小インスタンスが 0 でも、このテーマで destroy が必要な理由を説明できる。
