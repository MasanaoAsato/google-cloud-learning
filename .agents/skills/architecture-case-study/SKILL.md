# アーキテクチャケーススタディ

各ケーススタディの正本を `architectures/<テーマ>/README.md` に置く。サイト側は README をビルド時に取り込む。サイト用に同じ本文を別ファイルへ複製しない。

## 対象と情報源

1. ユーザーが指定した `architectures/<テーマ>` を対象にする。対象が無ければ候補を示して選んでもらう。複数テーマをまとめて更新する依頼では、テーマごとに同じ手順を繰り返す。
2. 変更前に対象の `README.md`、`architecture.svg`、Terraform、`README_TERRAFORM_DOCS.md`、関連する git 履歴を読む。既存の README に作成者の説明や失敗談があれば、一般論へ言い換えず残す。
3. README、Terraform、コミット、ユーザー入力から得た事実をメモする。サービスの設定、数値、責任分界、運用手順は、根拠のパスか公式資料を併記できるものだけを書く。
4. 料金、サービス仕様、推奨構成など変わり得る情報は、クラウドプロバイダの公式資料と公式 Pricing Calculator で確認する。このリポジトリでは Google Cloud Pricing Calculator を使う。別のプロバイダの構成では、そのプロバイダの公式計算機を使う。
5. 推測を事実として書かない。元の比較記録が無いときは、設計者の意図を断定せず「このケーススタディで比較した判断」と明記する。
6. 学習テーマの範囲を優先する。Terraform に無い監視、通知、高可用性、利用者認証、災害復旧などを、一般的な改善項目として追加しない。ユーザーが別テーマとして扱うと示した事項は、未実装ではなく範囲外として短く明記する。

## README の更新

`references/readme-template.md` を読んで、対象 README の既存説明の後にケーススタディを追加する。すでにケーススタディがある場合は、作成者が書いた具体的な説明を残して更新する。

- `architecture.svg` があれば、`![構成図の説明](./architecture.svg)` としてそのまま使う。図を描き直したり、ASCII 図で置き換えたりしない。
- コード節には公開リポジトリの対象フォルダへの GitHub リンクを置く。origin URL から安定したリンクを作れない場合は、相対リンクを残し、公開 URL が未確定であることを報告する。
- `terraform-docs architectures/<テーマ>` を実行して `README_TERRAFORM_DOCS.md` を更新する。README からその出力へリンクする。`.terraform-docs.yml` の `BEGIN_TF_DOCS` と `END_TF_DOCS` の間にはケーススタディ本文を書かない。生成のたびに消える。
- README とサイトの内容を一致させるため、同じ文章をサイト固有の MDX、HTML、JSON にコピーしない。必要ならサイトのビルド設定だけを README 参照へ変える。
- ユーザーが一時作成・削除を前提にした場合は、月額の常設構成を主題にしない。作成時間、確認項目、削除手順を中心に書き、常設時の月額は必要な比較情報に留める。

## 設計判断

各 ADR で、次を短く具体的に書く。

- その判断が必要になった業務上の条件
- 選んだサービスまたは設定
- 比較した代替案と、採用しなかった理由
- 受け入れた制約、コスト、運用負担

構成に存在する全サービスを ADR にしない。スケーリング、ネットワーク境界、データ保護、可用性、費用に効く判断に絞る。判断がコードや記録から復元できない場合は、空のもっともらしい ADR を追加せず、改善余地に「判断記録が無い」と書く。

## コスト、セキュリティ、運用

- コストは月額概算として示す。リージョン、稼働時間、リクエスト、保存量、転送量、通貨、計算日を前提に置く。料金表だけを並べず、固定費と利用量で変わる費用を分ける。未算入の費用も書く。実際の請求額と読める表現は使わない。
- IAM は、誰のサービスアカウントにどのロールを渡すか、Terraform から確認できる範囲で書く。テーマ外の未実装項目を改善候補として列挙しない。
- 障害時の記述は、テーマ内で実装・確認するものだけを書く。実際に自動化されていない操作を「自動復旧」と呼ばない。
- 公開前に、プロジェクト ID、組織名、個人名、メールアドレス、内部ホスト名、IP、秘密情報を探す。実値を残さず、必要ならプレースホルダへ置換する。

## 文体の仕上げ

下書き前と推敲後に、`.agents/skills/stop-ai-slop-jp/SKILL.md` と必要な参照ファイルを読む。ユーザーの入力にある具体的な事情、数値、迷い、失敗を根拠のある範囲で残す。体験していない苦労や感情を作らない。

- 各節に、誰が何を選び、何を運用するのかを書く。抽象語や無生物を主語にして、判断を曖昧にしない。
- 見出しはテンプレートの名詞句を使う。節ごとに結論の型や段落の長さを揃えすぎない。
- 「重要」「最適」「本質的」で逃げず、設定値、運用手順、代替案、費用前提へ下ろす。全方位的な肯定はしない。
- 全角ダッシュ、飾りの絵文字、不要な引用符、三項並列、横文字の比喩、テンプレート調の結論を削る。
- 仕上げに stop-ai-slop-jp の 5 軸を採点し、35/50 未満なら書き直す。

## 完了確認

次を確認してから報告する。

- 7 節が README にそろい、各節の内容が一次情報または公式資料に戻れる。
- 構成図は既存 SVG を参照し、コード節にはフォルダと terraform-docs 出力へのリンクがある。
- ADR に理由、代替案、トレードオフがあり、推測した部分は推測と分かる。
- コスト試算には前提、計算日、未算入項目がある。
- セキュリティと運用では実装済みとテーマ外の事項が混ざっていない。
- README 外に本文のコピーを作っていない。生成済み terraform-docs 節を壊していない。
- 公開してよい情報だけになっている。
