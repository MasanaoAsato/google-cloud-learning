# 学習テーマまとめ HTML ジェネレータ

## リポジトリ設定

**このスキルを別リポジトリにコピーしたら、まずこの表だけを書き換える。**
以下の本文とテンプレートはすべてこの表の値を参照しており、他に直す箇所は無い。

| キー | 本リポジトリでの値 |
|---|---|
| `THEME_ROOT` | `architectures` |
| `IAC` | Terraform（コード拡張子 `.tf`、設定値は `local.tf`） |
| `CLI` | `gcloud` |
| `DOCS` | Google Cloud 公式ドキュメント |
| `REPO_NAME` | `google-cloud-learning` |

以降、`<テーマ>` はテーマディレクトリ名（`10` など）、`<テーマパス>` は `THEME_ROOT/<テーマ>` を指す。

> 別リポジトリでの記入例（Azure / Bicep の場合）:
> `THEME_ROOT=architectures` / `IAC=Bicep`（`.bicep`、`main.bicepparam`）/ `CLI=az` /
> `DOCS=Microsoft Learn` / `REPO_NAME=azure_iac_practice`
>
> `evals/evals.json` はリポジトリ固有のテストデータなので、移植先では書き直すか空にする。

## このスキルが解こうとしている問題

このリポジトリは「クラウドのアーキテクチャを IaC で書いて学ぶ」ためのもので、
`THEME_ROOT` の下にテーマごとのディレクトリが切られている。

apply して動かした直後は理解しているつもりでも、数週間経つと
**「このテーマで結局何が身についたのか」「それをどう確かめれば思い出せるのか」** が失われる。
コードは残るが、コードは「何を学ぶためにこう書いたのか」を語らない。

このスキルが作るのはその欠落を埋める 1 枚の HTML。読み手は将来の本人か、初めてこのテーマを見る人。
求められているのは仕様の再掲ではなく **「手を動かして確かめ直せる形の理解」** である。

設計の中心は 2 つ。

> **1. 学びポイントには必ず、それを自分の目で確認する手段が紐づいていること。**
> 確認できない学びは読んだ気になるだけの箇条書きに劣化し、
> 「それで何がわかるのか」の無いコマンド集も同じく役に立たない。両者を対にすることが価値のほぼすべて。
>
> **2. 5 分で読み切れること。**
> 網羅した長い資料は開かれなくなる。開かれない資料の情報量はゼロ。
> 削る判断こそがこのドキュメントを書く仕事の中身だと思ってよい。

## 分量の予算（最優先の制約）

読む負担が増えた瞬間にこのドキュメントは死ぬ。以下を上限として扱い、超えたら足すのではなく削る。

| 部位 | 上限 |
|---|---|
| 全体 | **A4 で 2〜3 ページ / HTML 25KB 前後**（CSS 込みで 35KB を超えたら書きすぎ） |
| 学びポイント | **3〜5 個**、本文は各 **2〜3 文** |
| 確認シナリオ | 学びと同数。手順は **5 行以内**のコマンド、期待結果は **箇条書き 3 個以内** |
| 設計の要点 | **3 項目以内**、各 **1〜2 文**。無ければ丸ごと省略してよい |
| つまずき | **実際に踏んだ・確実に踏むものだけ 0〜3 個**。埋めるための水増しは書かない |
| 参考リンク | **3〜6 件** |

「書けることを全部書く」と必ず 5 ページを超える。**書かなかったことはコードを読めば分かる**、
という前提に立って切り捨てること。判断に迷ったら削る側に倒す。

## 手順

### Step 1: 対象テーマを確定する

ユーザーが `<テーマパス>` のように指定していればそれを使う。番号だけ（「10 の」）の場合も同じ。
指定がなければ `ls <THEME_ROOT>/` の結果を見せて選んでもらう。

出力先は既定で `<テーマパス>/summary.html`。
**既にファイルがある場合は上書き前に必ず読む** — 前回の記述にユーザーが手を入れている可能性があり、
その加筆は生成物より価値が高い。差分を活かして更新し、「上書きするが以前の記述は取り込む」と伝える。

### Step 2: 情報を集める（1 パスで済ませる）

`scripts/collect_context.sh <テーマパス>` を実行すると、IaC コード・既存ドキュメント・
git 履歴が 1 回でまとめて出力される。個別に Read を積み重ねるより速く、見落としも減る。
このスクリプトはテーマパスを引数で受け取るだけで、クラウドにもディレクトリ名にも依存しない。

```bash
bash <skill-dir>/scripts/collect_context.sh <テーマパス>
```

出力が切り詰められたファイルだけ個別に Read する。**探索を広げすぎない** — このドキュメントは
テーマ 1 つの理解を助けるものであって、リポジトリ全体の監査ではない。

情報源ごとの読み方:

- **IaC コード** — 事実の一次情報。設定値をまとめたファイル（Terraform なら `local.tf`）、
  モジュール間の依存、そして「わざわざそう書いてある」引数に注目する。意図的に値を散らしてある設定
  （キャッシュ制御を種類ごとに変えてある等）は、ほぼ確実に学習の主題そのもの。
  デフォルトのまま書かれた引数と、意図をもって選ばれた引数を区別する。
- **ROADMAP.md / README.md** — あれば最優先。ユーザー自身が言葉にした学習の軸がそこにある。
  勝手に言い換えず、その軸を骨格として採用する。ROADMAP の「完了の定義」は
  学びポイントと確認手段の下書きとしてそのまま使えることが多い。
  なお既存ドキュメントの記述がコードや公式仕様と食い違っていたら、**黙って直さず矛盾として指摘する**。
  本人の誤解に気づける瞬間は、まとめが提供できる価値の中でも大きい。
- **git 履歴** — コミットメッセージから試行錯誤の跡が読める。そこは本人がつまずいた場所。
- **`DOCS`（公式ドキュメント）** — **記憶で断定できない仕様に限って**引く（目安 3 件まで）。
  ヘッダ名・既定 TTL・エラーコードなどを記憶で書かない。間違った仕様が書かれたまとめは
  無いより有害になる。逆に、自明な内容の裏取りに時間を使うのは無駄。

### Step 3: 学びポイントと確認手段を対にして設計する

HTML を書き始める前に、この対応表を作る。ここが実質的な設計作業であり、分量を決める工程でもある。

- 学びポイントは **3〜5 個**。テーマの主題から外れる細部は「構成」表に事実として置くに留め、
  学びポイントに昇格させない。
- 各ポイントは「何がわかるか」ではなく **「何を理解した状態になるか」** で書く。
  「CDN の設定」ではなく「オリジンの `Cache-Control` が CDN の保持挙動をどう決めるか」。
- 確認手段は **観測できる差** を作るものにする。「動くことを確認」は確認になっていない。
  2 回叩いてヘッダが変わる、設定違いの 2 つのオブジェクトで結果が割れる、といった
  **対比が出る**手順を選ぶと、そこで初めて理解が検証される。
- 実行時にしか決まらない値（LB の IP、生成された suffix）は決め打ちせず、
  取得コマンドを先に置いて `$LB_IP` のようなシェル変数として使わせる。
- **コマンドは実在するものだけ。** `CLI` のサブコマンドは似た名前で存在しないことがある。
  記憶があいまいなら `CLI <group> --help` を実行して確かめる。
  打てないコマンドが載っていると、確認手順そのものが信用を失う。

対応が付かない学びポイントが残ったら、粒度が大きすぎるか、確認手段をまだ思いついていないだけ。
分解するか、`CLI ... describe`（設定値を目視確認する形）まで落とす。

### Step 4: HTML を生成する

`assets/template.html` をコピーし、プレースホルダを埋める。テンプレートには
配色（ライト/ダーク自動切替）・印刷用スタイル・コマンドのコピーボタン・理解度チェックの保存が
入っているので、CSS や JS を書き直す必要はない。構造とスタイルは変えず、中身だけ差し替える。
`<title>` の `{{リポジトリ名}}` には `REPO_NAME` を入れる。
**下書きを長く書いてから削るのではなく、最初から予算内で書く。**

構成図は自前で描かない。`<テーマパス>/architecture.svg`（または `.drawio`）があれば
それを参照するのが最善で、テキストのボックス図はその劣化コピーにしかならない。
図が無いときだけ、テンプレートの簡易フロー（3 行以内）を使う。
モジュール内部の素材 SVG（`modules/*/src/assets/*.svg` など）は構成図ではないので混同しない。

各セクションに何を書くか、良い例・悪い例は `references/content-guide.md` にある。

書き終えたらブラウザで開いて見せる:

```bash
open <テーマパス>/summary.html
```

### Step 5: 事実確認して報告する

生成後、自分の出力を疑って次を確かめる。ここを飛ばすと「もっともらしいが間違っている」まとめが残る。

- 書いた設定値（メモリ、タイムアウト、TTL、パス）が実際の IaC コードと一致するか
- コマンドが実在し、対象テーマの構成に対して意味を成すか
- 各学びポイントに確認シナリオへのリンクが張られ、リンク先が実在するか
- 予算（A4 2〜3 ページ）に収まっているか。超えていれば削ってから出す
- 公式ドキュメントのリンクが実在する URL か
- **実プロジェクト ID・アカウント名・メールアドレス・ホスト名・IP を書いていないか。**
  実測値に触れる場合も識別子はプレースホルダ（`your-project-id` 等）に置く。
  このまとめは公開される前提で書く

ユーザーへの報告では、**推測で補った箇所や未検証の挙動を明示する**。
学習用ドキュメントでは「どこが確かでどこが仮説か」の区別自体が学習材料になる。

## 品質の基準

**書いてよいのは、コードから読めた事実・ドキュメントで裏取りした仕様・本人の記録（ROADMAP/コミット）の 3 つだけ。**
それ以外の「たぶんこうだろう」は書かないか、仮説と明示する。

**分量よりも対応関係。** 学びポイント 4 個にそれぞれ確認シナリオが付いた 1 枚は、
学びポイント 12 個の箇条書きより役に立つ。網羅は目的ではない。

**将来の本人が読む文体で。** 「〜と考えられます」より「〜になる。理由は〜」。
このリポジトリの既存 ROADMAP.md の口調（断定・簡潔・理由を添える）に寄せると馴染む。

**コストと後始末は必ず書く。** 課金が続くリソース（LB、ストリーミングジョブ、min instance > 0）が
あるテーマでは destroy コマンドと残存確認コマンドを必ず入れる。
学習用リポジトリで最も高くつく失敗がこれ。ただし後始末が必要だからといって、
つまずきポイントまで埋めようとしないこと — 実話が無ければ後始末だけでよい。

## 参照ファイル

- `references/content-guide.md` — セクション構成、各セクションの分量と書き方、良い例/悪い例。
  HTML を書く前に読む。
- `assets/template.html` — 1 ファイル完結の HTML テンプレート。コピーして中身を差し替える。
- `scripts/collect_context.sh` — IaC コード・ドキュメント・git 履歴を一括収集。引数はテーマパスのみ。
- `evals/evals.json` — このリポジトリ固有の eval セット。移植先では書き直す。
