# セクション構成と書き方のガイド

`assets/template.html` のセクションはこの順で並んでいる。各セクションに何を入れるか、
**どこまでで打ち切るか**、そして役に立つ記述と役に立たない記述の境界。

パス・CLI・公式ドキュメントの表記は SKILL.md の「リポジトリ設定」に従う
（`<テーマパス>` = `THEME_ROOT/<テーマ>`、`CLI`、`IAC`）。

具体例は本リポジトリのテーマ（Google Cloud の CDN / Dataflow）から引くが、
**書きぶりの見本であって内容の流用元ではない**。別クラウドのリポジトリでも、
「良い/悪い」の判断基準はそのまま通用する — サービス名を読み替えて使うこと。

## 目次と分量

| # | セクション | 分量の上限 | 省略可 |
|---|---|---|---|
| 1 | [ヘッダー](#1-ヘッダー) | 3 行 + チップ数個 | 不可 |
| 2 | [このテーマで学ぶこと](#2-このテーマで学ぶこと) | 3〜5 個 × 2〜3 文 | 不可 |
| 3 | [何を作ったか](#3-何を作ったか) | 図の参照 + 表のみ | 不可 |
| 4 | [設計の要点](#4-設計の要点) | 3 項目 × 1〜2 文 | **可** |
| 5 | [どう確認するか](#5-どう確認するか) | 学びと同数 | 不可 |
| 6 | [後始末とつまずき](#6-後始末とつまずき) | 後始末 + つまずき 0〜3 個 | つまずきは可 |
| 7 | [理解度チェック](#7-理解度チェック) | 4〜5 個 | 可 |
| 8 | [参考リンク](#8-参考リンク) | 3〜6 件 | 可 |

全体で A4 2〜3 ページ。**この表は目標ではなく上限**で、下回るのは歓迎される。

---

## 1. ヘッダー

テーマ番号、タイトル、一行サマリ、メタ情報チップ（主要プロダクト / 課金の有無）。

タイトルは「Architecture 10」だけでは思い出せない。**主題を名乗らせる**。

- 良い: `10 — Cloud CDN: キャッシュを「誰が」「どの指示で」持つのか`
- 悪い: `10 — Cloud Storage と Cloud Run と Load Balancer`（部品の列挙は主題ではない）

一行サマリは「このテーマの問いは何か」。`LB 配下で静的配信と API を出し分け、オリジンの
Cache-Control が CDN の挙動をどう決めるかを実測で確かめる。` のように問いと確かめ方を入れる。

## 2. このテーマで学ぶこと

**このドキュメントの主役。3〜5 個、各 2〜3 文。** 各ポイントは次の 3 要素を持つ。

| 要素 | 中身 |
|---|---|
| 見出し | 理解した状態を一文で。名詞の羅列にしない |
| 本文 | なぜ重要か / 他テーマとどう繋がるか（**2〜3 文で止める**） |
| 確認リンク | 対応する検証シナリオへのアンカー（`#check-N`） |

見出しの粒度:

- 良い: `オリジンが返す Cache-Control が、CDN の保持期間とブラウザの再検証を同時に決める`
- 悪い: `Cloud CDN について`（何を理解したのか判定できない）
- 悪い: `enable_cdn = true にする`（設定手順であって理解ではない）

本文で書く価値があるのは「**なぜ**」だけ。仕様の言い換えは要らない。

- 良い: `キャッシュ制御はインフラ側の設定ではなくオブジェクトのメタデータで決まる。
  配信の速さと鮮度のトレードオフは、LB ではなくコンテンツを置く側の責務になる。`
- 悪い: `Cloud CDN はコンテンツをエッジにキャッシュして配信を高速化するサービスです。`
  （公式ドキュメントの要約。読み手はもう知っている）

6 個目を書きたくなったら、それは主題が 2 つ混ざっているか、粒度が細かすぎる。統合するか捨てる。

## 3. 何を作ったか

コードを開かなくても構成が頭に入る状態にする。**このセクションは短くてよい** —
学びでも確認でもないので、長い散文はまるごと無駄になる。

**(a) 構成図** — `<テーマパス>/architecture.svg`（または `.drawio`）があるなら、
テンプレートの `.diagram` ブロックでそれを参照する。自前のテキスト図は劣化コピーにしかならない。
図が無いときだけ簡易フロー（3 行以内、分岐条件だけラベルに書く）を使う。

```
Client → Global LB → /api/*  → Cloud Run（動的）
                   → その他 → Backend Bucket + Cloud CDN → GCS（静的）
```

**(b) モジュール表** — `モジュール / 役割 / このテーマ的に効いている設定` の 3 列。
役割は **1 行**。最後の列に `local.tf` の**実際の値**を書く（記憶や一般的な既定値で埋めない）。
表の後に説明文を足したくなったら、それは学びポイントか設計の要点に属する内容。

## 4. 設計の要点

「そう書いてある」を「そう書いた理由」に変える。**3 項目まで、各 1〜2 文。無ければ省略。**

拾う価値があるのは:

- 選択肢があったのに一方を選んでいる箇所（`cache_mode`、classic か flex か、GA か beta か）
- 意図的に不揃いにしてある値（オブジェクトごとに違う `cache_control`、片方だけ `enable_cdn = true`）
  — ほぼ確実に実験の仕掛け
- 学習用の割り切り（認証なしの公開、HTTP のみ、削除保護なし）。
  **割り切りだと明示する**のが目的なので、まとめて 1 項目でよい

裏取りできなかった理由は「仮説」と明示する。断定した誤りより、仮説と分かる推測の方が安全。

## 5. どう確認するか

学びポイントと対になる、手を動かす手順。**各シナリオは 4 パートで固定**する。
形が揃っていると、後日どこから読んでも迷わない。

1. **確かめること** — 一文
2. **手順** — コピペで動くコマンド（**5 行以内**）
3. **期待される結果** — 何がどう見えれば成功か（**箇条書き 3 個以内**、ヘッダ名・値まで具体的に）
4. **これでわかること** — 観測と理解の接続（**1〜2 文**）。ここが抜けると単なるコマンド集になる

### コマンドの書き方

実行時にしか決まらない値は、**先に取得コマンドを置いて変数に入れる**。決め打ちは必ず腐る。

```bash
# 良い（IaC の output から引く。THEME_ROOT=architectures / IAC=Terraform の場合）
LB_IP=$(terraform -chdir=architectures/10/main output -raw lb_ip)
curl -sI "http://$LB_IP/assets/cacheable.txt" | grep -i -E 'cache-control|cache-status|age'

# 悪い
curl -sI http://34.123.45.67/assets/cacheable.txt   # 次の apply で変わる
```

実 IP・実プロジェクト ID・実アカウント名を手順に焼き込まない。**腐るから**であり、
同時に**このまとめは公開される前提だから**でもある。識別子は必ず変数か
プレースホルダ（`your-project-id` など）にする。

出力が長いコマンドは `grep` / `--format` / `jq` で**見るべき行だけに絞る**。
絞り込み自体が「どこを見ればよいか」の教材になる。

そして **存在するコマンドだけを書く**。`CLI` は似た名前のサブコマンドが無いことがある
（`gcloud compute security-policies rules` に `list` は無く、`describe` で policy 全体を見る）。
あいまいなら `--help` で確認する。打てないコマンドは確認手順全体の信用を落とす。

### 良い検証シナリオの条件: 対比が出ること

「動いた」は確認ではない。**設定の違いが結果の違いとして現れる**手順を選ぶ。

- 良い: 同じ URL を 2 回叩き、1 回目 `Cache-Status: miss` → 2 回目 `hit` を見る
- 良い: `cacheable.txt`（`max-age=300`）と `no-store.txt` を叩き比べ、片方だけ hit する
- 悪い: `curl http://$LB_IP/` で 200 が返るのを確認する（何を検証したのか不明）

IaC の plan 差分を読む、`CLI ... describe` で設定値を見る、コンソールのメトリクスを見る、
も立派な確認手段。課金や時間がかかる場合は所要時間と概算コストを一言添える。

## 6. 後始末とつまずき

**後始末は必須、つまずきは実話があるときだけ。**

後始末: 何が課金対象として残るか（1 文）と、destroy + 残存確認コマンド。

```bash
# IAC の destroy コマンド + CLI での残存確認（下は Terraform / gcloud の場合）
terraform -chdir=architectures/10/main destroy
gcloud compute forwarding-rules list   # 残っていないことの指差し確認
```

つまずき: **0〜3 個**。git 履歴の「修正」コミット、ROADMAP に書かれた失敗、
コードを読んで確実に踏むと分かるもの（プレースホルダのままのプロジェクト ID、
反映待ちを故障と誤認する類）だけ。**セクションを埋めるために一般論を並べない** —
「名前が衝突することがあります」のような誰にでも書ける注意書きは、読み手の時間を奪うだけ。
書くことが無ければ後始末だけで終える。

## 7. 理解度チェック

「自分の言葉で説明できるか」を問う 4〜5 個。ROADMAP の「完了の定義」があればそれを土台にする。
学びポイントと 1 対 1 で対応させると自然に収まる。

- 良い: `CDN がキャッシュを持つ/持たないの判断を、どのヘッダのどの値が決めているか説明できる`
- 悪い: `Cloud CDN を理解した`（判定できない）

**設定を思い出せるか**ではなく**理由を説明できるか**を問う。前者はコードを見れば済む。

## 8. 参考リンク

- 公式ドキュメントは**実在確認したもの**を 3〜6 件。網羅リストにしない
- 前後の関連テーマ（`<テーマパス>/ROADMAP.md` など実在するリポジトリ内パス）
- 未消化の発展課題があれば「次にやるなら」を 1〜2 個

## 削るときの優先順位

予算を超えたら、この順で落とす。

1. 設計の要点（セクションごと消してよい）
2. つまずきポイント（後始末だけ残す）
3. 学びポイントの本文の 3 文目以降
4. 参考リンク
5. 理解度チェック

学びポイントと確認シナリオの対応だけは最後まで残す。それが無ければこのドキュメントは存在意義を失う。
